# Анализ веб‑сервера TenZilla и предложения по оптимизации

## Текущее состояние

### HTML‑страница
- **Хранение:** одна большая строка `html_page[]` в **PROGMEM** (flash). RAM для самой страницы не используется — это уже оптимально.
- **Размер:** ~2400 строк (оценка ~100–120 KB) в одном `R"rawliteral"` в `TenZillaWeb.cpp`.
- **Доставка:** `server.send_P(200, "text/html", html)` — отправка из flash, без копирования всего объёма в RAM. Буфер WiFi отправляет чанками.
- **Изображения:** в разметке **нет** картинок (`.png`, `.jpg`, base64 и т.п.). Кнопки нарисованы через CSS (`::before`/`::after`). Убирать нечего.

### Опрос (polling)
- **`/api/scale`:** вызывается каждые **200 ms** (~5 запросов/с) через `setInterval(updateMainData, 200)`.
- **`/status` (WiFi):** каждые **3000 ms**.
- **`/api/motor/limits/status`:** каждые **2000 ms**.

Даже при одном клиенте 5 req/s на `/api/scale` дают заметную нагрузку на CPU, WiFi и JSON.

### Обработчик `/api/scale` (handleScaleData)
- Собирает ответ через `String response` и множество `+=`.
- Каждый `+=` может вызывать реаллокацию → фрагментация кучи и лишние копирования.
- Ответ содержит десятки полей (вес, калибровка, NTP, программа, энкодер и т.д.).
- Вызов выполняется в задаче веб‑сервера (Core 1); масштабных блокировок нет, но сборка JSON и отправка — дорого при 5 req/s.

### Вкладки
- Все вкладки (СЖАТИЕ, РАЗРЫВ, WiFi, Тензодатчик, Двигатель, Прочие) загружаются сразу.
- `updateMainData` обновляет DOM **всех** вкладок при каждом ответе `/api/scale`, независимо от активной.
- `updateWifiStatus` и `updateLimitsStatus` работают постоянно, даже когда открыты другие вкладки.

## Рекомендации (по приоритету)

### 1. Снизить частоту опроса и сделать его «таб‑зависимым» (максимальный эффект)

**Проблема:** 5 запросов/с к `/api/scale` создают основную нагрузку.

**Что сделать:**
- Хранить в JS текущую вкладку (например, `currentTab`) при переключении через `showTab()`.
- Опрос `/api/scale` с интервалом **200 ms** выполнять **только** при активной вкладке **СЖАТИЕ**, **РАЗРЫВ** или **Тензодатчик**.
- На вкладках **WiFi**, **Двигатель**, **Прочие** либо не вызывать `updateMainData`, либо вызывать редко (например, раз в **5–10 s**) только если нужна синхронизация с TFT (например, `currentScreen`).

**Дополнительно:**
- `updateWifiStatus` вызывать только когда открыта вкладка **WiFi**.
- `updateLimitsStatus` — только когда открыта вкладка **Двигатель**.

**Эффект:** в типичном сценарии (пользователь на одной вкладке) число запросов к `/api/scale` падает с 5/с до 0/с при работе с WiFi/Двигатель/Прочие, плюс реже идут запросы к `/status` и `/api/motor/limits/status`.

---

### 2. Увеличить базовый интервал опроса `/api/scale`

**Сейчас:** 200 ms.

**Предложение:** 300–400 ms (≈2.5–3 обновления в секунду). Для панели управления этого обычно достаточно, а нагрузка снижается.

**Эффект:** при активной вкладке с весами количество запросов уменьшается примерно в 1.5–2 раза.

---

### 3. Оптимизировать `handleScaleData` (меньше аллокаций, меньше нагрузки на CPU)

**Проблема:** много операций `String +=`, реаллокации, фрагментация кучи.

**Варианты:**

- **Вариант A:** вызвать `response.reserve(1024)` (или подходящий размер) в начале и дальше использовать `+=`. Это уменьшит число реаллокаций.
- **Вариант B:** собирать JSON в буфер фиксированного размера (`char buf[1024]`) через `snprintf` и отправлять его (например, через `server.send(200, "application/json", buf)`). Избегаем `String` и динамической кучи в этом handler’е.

**Эффект:** меньше нагрузка на heap и CPU при каждом запросе `/api/scale`.

---

### 4. Не отправлять повторный запрос, пока предыдущий не завершён

**Проблема:** при медленном WiFi или кратковременной задержке ответа таймер может порождать новый `updateMainData` до завершения предыдущего → несколько одновременных XHR к `/api/scale`.

**Что сделать:** флаг `scaleRequestInFlight`. В `updateMainData` перед `xhr.open` проверять флаг; если запрос уже идёт — выходить. В `onreadystatechange` при `readyState === 4` сбрасывать флаг.

**Эффект:** не больше одного активного запроса к `/api/scale`, нет накопления очереди при «подвисаниях».

---

### 5. Разбить HTML на части (по желанию)

**Идея:** не одна строка в PROGMEM, а несколько кусков (например, head+CSS, body‑каркас, вкладки) и отправка через `sendContent_P()` чанками.

**Плюсы:**
- Удобнее поддерживать (меньше гигантских литералов).
- Теоретически можно чуть снизить пиковое использование буфера отправки, но на практике ESP32 WebServer и так стримит из flash.

**Минусы:**
- Нужно вручную собрать chunked‑ответ (заголовки, `sendContent_P` по частям). Кода больше.
- Выигрыш по быстродействию и нагрузке небольшой по сравнению с пунктами 1–4.

**Вывод:** имеет смысл только если хочется упростить структуру кода; для производительности приоритет низкий.

---

### 6. Хранить страницу в RAM («как раньше»)

**Сейчас:** HTML в PROGMEM, при отправке читается из flash. RAM под саму страницу не используется.

**Если хранить в RAM:** нужен объём порядка 100–120 KB. На ESP32 это возможно (например, из heap или PSRAM), но:
- освободившаяся flash почти не даёт выигрыша по скорости веб‑сервера;
- отправка всё равно идёт через тот же WiFi и те же буферы;
- увеличится потребление RAM и риск OOM при других операциях.

**Вывод:** **не рекомендуется**. Текущий вариант с PROGMEM лучше.

---

### 7. Убрать картинки

В разметке картинок нет, только CSS‑фигуры. Действовать нечего.

---

### 8. Дополнительно (по возможности)

- **Cache / Etag для `GET /`:** при повторном открытии страницы можно отдавать `304 Not Modified`, если контент не менялся. Тогда повторно HTML не передаётся. Требует хранения/вычисления Etag и обработки `If-None-Match`.
- **Минификация CSS/JS:** убрать лишние пробелы, комментарии. Уменьшит размер HTML и чуть ускорит загрузку. Можно делать на этапе сборки или вручную при правках.

## Итоговый приоритет внедрения

| № | Действие | Сложность | Влияние на нагрузку/быстродействие |
|---|----------|-----------|-------------------------------------|
| 1 | Таб‑зависимый опрос + реже статусы WiFi/limits | Средняя | **Высокое** |
| 2 | Интервал `/api/scale` 200 → 300–400 ms | Низкая | **Высокое** |
| 3 | Оптимизация `handleScaleData` (reserve или buf) | Низкая | **Среднее** |
| 4 | Не слать новый `/api/scale`, пока предыдущий в полёте | Низкая | **Среднее** |
| 5 | Разбить HTML на части / chunked | Высокая | Низкое |
| 6 | Хранить HTML в RAM | Низкая | Не рекомендовано |
| 7 | Убрать картинки | — | Нет (их нет) |

Оптимально начать с **1–4**: они дают наибольший выигрыш при умеренных изменениях кода.
